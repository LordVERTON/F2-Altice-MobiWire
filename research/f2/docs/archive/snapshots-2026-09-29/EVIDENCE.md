- **Fait observé par l'utilisateur :** Multimedia affiche Image Viewer et FM Radio; aucun Audio Player actuellement visible.
- **Analyse statique :** menu descriptor : parent U16 `+0x14`, sélection `+0x18`, buffer enfants `+0x40`, nombre `+0x48`; valeurs numériques Multimedia et relations de launch non établies. Source : `work/ghidra/alice_reports/menu_child_launch_map.txt` et rapports associés.
- **Analyse statique :** aucune entrée AudioPlayer, init ou launch handler n'a été attribué dans la reconstruction actuelle. Le registre dynamique peut encore cacher une app compilée; conclusion d'absence non justifiée. Source : `work/ghidra/alice_reports/altice_menu_reconstruction.txt`.
- **Interprétation prudente :** une nouvelle ligne de menu seule ne rendrait pas un lecteur fonctionnel sans launch target valide, dépendances et décodeur compatible.
- **Documentation produit :** le manuel utilisateur NIKITI / Altice F2 décrit Audio Player et Video Player dans Multimedia (Video formats 3GP/MP4/AVI). Source consultée : [section Video Player/Audio Player du manuel](https://www.manualslib.com/manual/3026709/Sfr-Altice-F2.html?page=79). Cela documente le comportement attendu du modèle, pas nécessairement le contenu de chaque build logicielle.
- **Écart build documenté :** un rapport réglementaire FCC pour le même nom de modèle NIKITI / Altice F2 et HW V01 cite le logiciel `ELKI_DS_L_V01.2_181106_MP` ([rapport EMC FCC](https://fccid.io/m/99e9d1ca8c8434c84f5158661b6071dd7c65ffb8c7b53a8742daf84065ff150b.pdf)). Le dump de cet appareil est `ALTICE_F2_DS_V02.1_181023_MP`. C'est une différence de build confirmée; son effet sur les applis Multimedia reste à vérifier, car le binaire ELKI exact n'est pas disponible.
- **Mécanisme de menu :** ALICE récupère les IDs enfants par l'API plateforme `0xF032ACDC` et leur nombre par `0xF02D8870`, sur la base du parent dynamique au descripteur `+0x14`; leurs implémentations/data ne sont pas dans le package ROM/VIVA de service. Les deux éléments visibles sont donc une liste issue du registre/runtime, pas des chaînes statiques prouvant quels exécutables existent. Détails : `work/ghidra/alice_reports/menu_external_api_resolution.txt` et `multimedia_app_presence_analysis.txt`.
- **Tracé launch, 2026-09-28 :** `FUN_1021F904` consomme le flag d'activation et l'ID sélectionné, puis appelle `FUN_102BA458`; cette dernière ne pousse un nouvel ID parent/redessine que si le bit runtime « enfant avec sous-menu » est posé. Aucun launch de feuille Image Viewer/FM n'est visible dans ce chemin, et aucun callback cible n'est attribué. IDs, init et launch restent **UNKNOWN**; le registre/dispatcher feuille est externe ou dans un chemin différent. Voir `work/ghidra/alice_reports/multimedia_registration_launch_trace.txt`.
- **Conclusion causale provisoire :** différence de variante/build ou modules non enregistrés/désactivés est l'explication la mieux étayée. La documentation ne prouve pas que le build ALTICE_DS possède les mêmes applications. Une corruption sélective est moins probable, sans être impossible; contrainte mémoire/licence/opérateur demeure spéculative. Rapport : `work/ghidra/alice_reports/multimedia_app_presence_analysis.txt`.

## Audio / codec

- **Analyse statique, preuve forte :** backend/interface nommé `aud_player_media`; constructeur `0x102362A4`, contexte/consumer `0x10214940`, callbacks indirects et services génériques UI/resources documentés. Source : `work/ghidra/alice_reports/media_callback_structure.txt`.
- **Qualification après revue des callees :** le seul appelant direct connu du constructeur passe par un contexte orienté Bluetooth/A2DP. Les callbacks `0x1028D394/0x1028D378` appellent `0x1024EDD8` (création/configuration d'objet générique), `0x1024D162` (écriture d'un champ), `0x1024B758` (résolution courte chaîne/ressource), `0x102474C6` (fonction vide) et `0x1024EDA0` (finalisation). Cela ne prouve pas une ouverture/lecture de fichier ni un décodeur. La formulation antérieure « opérations fichiers/flux » dans `media_backend_trace.txt` est corrigée; voir sa note datée.
- **Limite :** callback vers UI générique ne prouve pas écran AudioPlayer ni navigation fichiers/playlist/play/pause.
- **Recherche de signatures :** `compare_audio_signatures.py` a trouvé les chemins média/audio génériques dans ALICE Altice, mais pas les chaînes ciblées `MP3`, `DAF`, `AudioPlayer`, `audio/mp3`, `audio/mpeg3`, `audio/x-mp3` ou `DYNAMIC_COMP_DAF` dans les images Altice analysées. Source de script : `scripts/analysis/compare_audio_signatures.py`.
- **Scan ciblé supplémentaire, 2026-09-28 :** `scripts/analysis/scan_mp3_codec_evidence.py` a relu l'image service 3 MiB, ROM (269,836 B), VIVA (2,395,836 B), ALICE décompressée/conteneur et dump NOR 2 en ASCII/UTF-16LE. Aucun chemin `format → codec init → playback` n'a été identifié. La ROM contient des tokens `MP33` (adjacent à `004`) et `MP36` (`002`) au milieu de 50 entrées de forme `MPxx/MMxx`; `MP33` figure aussi dans la ROM QMobile. Le sens de ces tags n'est pas résolu, donc ils ne prouvent pas la présence d'un décodeur MP3. Le QMobile a une liste texte de types/extensions MP3/MP4/AAC, mais c'est un autre build et ce n'est pas une preuve de décodage Altice.
- **Rapport/verdict actuel :** `work/ghidra/alice_reports/mp3_decoder_verdict.txt` = **UNCERTAIN**. Analyse ciblée, pas preuve d'absence.
- **Décompilation ciblée, 2026-09-28 :** `scripts/ghidra/DecompileAudioCodecNeighborhood.java` a exporté en lecture seule les fonctions près des chaînes source `WavDecoder.c` (0x101F6274) et `AmrParser.c` (0x102A0708). Les chaînes n'ont ni XREF Ghidra ni pointeur absolu reconnu. `FUN_101F6474` lit des données 16-bit et remplit un buffer, mais aucun format/codec n'est prouvé; certaines fonctions proches du marqueur AMR sont clairement du rendu UI, donc la proximité de la chaîne ne permet pas de les attribuer au codec. Aucun dispatch/init MP3 ou lien vers playback n'a été établi. Rapport : `work/ghidra/alice_reports/audio_decode_path_fast.txt` et détails : `audio_codec_neighborhood.txt`.
- **Interprétation — ajout « from scratch » :** un décodeur logiciel est théoriquement intégrable, mais ce n'est pas encore une voie démontrée/praticable. Il manque une chaîne de build/link reproductible pour ALICE, un contrat d'accès à la sortie audio/PCM et une méthode de validation. 4 MiB est la capacité NOR, pas la place libre; RAM et performances ne sont pas mesurées. Étape préalable : identifier APIs audio natives/ROM ou un SDK externe compatible.
- **Inventaire API/SDK local, 2026-09-28 :** aucun SDK MAUI/MRE ni header/lib d'application audio n'a été trouvé dans le workspace; le scan textuel des chaînes ROM/VIVA ciblées ne révèle pas d'API lisible. C'est une absence d'artefact/nom documenté, pas une preuve d'absence d'API : exports par ordinals ou pointeurs restent possibles. Le rapport `work/ghidra/alice_reports/audio_runtime_api_inventory.txt` fixe le prochain test : résoudre les exports ROM/VIVA et remonter des appels FM/voix jusqu'au sink pour savoir si un buffer PCM est accepté.
- **Support app MRE/VXP :** Ghidra trouve `[MRE VERSION] %d` dans ALICE, sans XREF reconnu; `.vxp`, `VXP`, `MRE API`, `J2ME`, `appdb`, `@mre` sont absents du scan ciblé. Le marqueur seul n'identifie pas un runtime d'applications. Une [note communautaire MT6261](https://gopherproxy.meulie.net/hoi.st/0/docs/own/maui-kb-mt6261.txt) rapporte que beaucoup de MAUI MT6261 récents manquent de J2ME/MRE, mais elle est générale et non officielle; support sur cet exemplaire = **UNKNOWN**, tendance défavorable.
- **Fait observé par l'utilisateur, 2026-09-28 :** le téléphone ne présente aucun menu Applications, Java ou installateur. Cela écarte le parcours utilisateur normal pour installer/lancer une application tierce. Cela ne démontre pas à lui seul l'absence d'un runtime caché ou d'un lancement via un mécanisme de service, mais l'app externe est écartée comme voie MVP actuelle.
- **Limite des APIs plateforme :** l'analyse combinée ROM/ALICE a déjà montré que des veneers ALICE pointent vers `0xF0xxxxxx` non mappés par le package service ROM/VIVA; les cibles documentées concernaient le menu, pas l'audio. L'implémentation du système/SoC n'est donc pas incluse dans les fichiers disponibles. Source : `work/ghidra/alice_reports/menu_external_api_resolution.txt`.
- **Limite de cette recherche :** les chaînes peuvent être absentes d'un composant opaque, compressé, externe ou d'un chemin sans noms lisibles. Le décodeur MP3 reste donc **UNKNOWN**, pas ABSENT.
- **À vérifier (prioritaire) :** suivre dispatcher de format, choix codec, decoder init, open/play, EOF/seek/durée autour du backend et composants décompressés. Le verdict `PRESENT/ABSENT/UNCERTAIN` exige une chaîne de code convergente. Test physique File Manager → MP3, sans patch, est un contrôle direct et réversible si l'utilisateur peut fournir un fichier test.
